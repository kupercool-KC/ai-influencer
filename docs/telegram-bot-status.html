Telegram control bot — today's build

Ivy Vale's launch pushed the Telegram bot from a single flat chat into a real multi-agent control surface, plus the security work that had to come with giving it more reach.

Conversation model

Per-tab conversations

Shipped

A persistent keyboard under the text box — 🔍 Scout 🎨 Generate 📤 Dispatch 💬 Chat — replaces the old inline menu. Tapping a tab switches which agent free-text messages go to.

  • Each tab keeps its own memory — telegram_chats.histories, keyed by tab — so switching never bleeds context between conversations.
  • Each tab has its own agent-focused system prompt (e.g. Scout mode proposes the exact /scout command for what you describe).
  • Slash commands still work from any tab, regardless of which one is active.
New capabilities — owner only

Read/write access to live data

Owner onlyShipped

In the owner's chat, Claude can read and update real Supabase rows — influencers, media_assets, expenses, activity_logs, scheduled_dispatches — so "what's Ivy Vale's audience?" or "update her voice to X" just works in plain language.

  • Cannot touch database schema, run migrations, or edit this repo's code — data rows only.
  • A second authorized user can chat in every tab but gets none of these tools — gated to the exact owner chat_id.

Sandboxed code execution — run_code

Owner onlyHigher risk

Explicitly requested: Claude can run a bash or Node script on a throwaway GitHub Actions runner and report the output back as a follow-up message. Contained deliberately, since this is real code execution reachable from a phone:

  • No access to this app's real secrets — Supabase, Buffer, Higgsfield, and the GitHub PAT are never passed to that job.
  • Read-only checkout — the job cannot push commits back to the repo.
  • Hard 5-minute timeout so a runaway script can't burn Actions minutes.
  • Treat the bot token and webhook secret like production credentials — either one (or the owner's Telegram account) leaking means arbitrary code execution here.
Security hardening

Fixed GitHub Actions script injection

Security

All three agent workflows (content-scout, higgsfield-generate, buffer-dispatch) were interpolating untrusted inputs (prompt, caption, niche…) directly into shell scripts. A value with shell metacharacters could have broken out and run arbitrary commands with that job's secrets in scope. Fixed by routing every input through env: instead.

Webhook now fails closed

Security

Previously, an unset TELEGRAM_WEBHOOK_SECRET meant the bot silently accepted any request. Now a missing secret rejects everything.

Prompt-injection defense on tool data

Security

The app's api/db/* endpoints have no auth layer yet, so a planted field value could in theory try to instruct Claude through a tool result. The owner's system prompt now explicitly flags tool output as untrusted data, never as commands to follow.

Bugs fixed today

Markdown parse errors dropping replies

Fixed

Bad Request: can't parse entities — a free-form Claude reply with an unmatched * or ` made Telegram reject the whole message. sendMessage now retries as plain text instead of failing silently.

Second user's menu tap did nothing

Fixed

Introducing the new tab keyboard silently dropped taps on the old inline menu (still on-screen for anyone who hadn't re-run /start). Legacy taps now switch tabs the same way, and always clear the button's loading spinner.

"Deploy Database Migrations" failing on every push

Fixed

Two migrations applied directly against Supabase mid-session were never committed as files here, so supabase db push rejected every deploy with "Remote migration versions not found in local migrations directory." Backfilled both files, content verified against the live schema.
